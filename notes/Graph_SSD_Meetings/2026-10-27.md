## Intro, Recapping What's Already Done
### Dense BFS Optimization
* In the pull stage of BFS, the vertexSubset is like a really big bitvector
* Maintain a coarser bitvector for better performance in the pull stage
	* Have a bit per page/block that says whether _any_ of the vertices of this page is in frontier
	* Saves work by skipping whole pages with a single lookup in practice even though in theory this doesn't improve worst case
### Graph Compression
* You normally take your edge weights stored in CSR according to some carefully chosen vertex ordering
	* Ginger paper was emailed to everybody
* We want to do integer compression on the deltas between the adjacency list entries
	* Better compression quality corresponds to faster reads over the graph as we use less throughput, so long as decompression doesn't slow down by too much
* Ligra, Ligra+ use a continue bit per byte, so larger deltas need more bytes
	* More or less you try and shove the integer into a byte, and if it doesn't work overflow it to the next byte and you keep doing this
	* Decoding is then sequential as you need to decode the first $k$ integers before knowing where integer $k+1$ starts
* StreamVByte has a different approach that also allows you to do SIMD decoding
	* Every four integers to be decoded gets a single control byte, which encodes the number of bytes for each of the four integers
		* Must be $1,2,3,4$ bytes in StreamVByte
	* So then you read the control byte, then read the next 16 bytes (the next 4 integers take at most $16$ bytes) and do a SIMD shuffle to extract the four integers and place them at the right spots to do a SIMD read to extract the four numbers
		* The mask for the shuffle comes from a table lookup on the control byte
* The Ginger paper generalizes this with each neighbor list getting its own cookbook
	* Instead of using $1,2,3,4$ as the possible byte values choose values that get better compression quality
	* StreamVByte like performance with better compression quality
